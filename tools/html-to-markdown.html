What converts, and what is dropped

Headings become # markers, paragraphs stay paragraphs, bold and italic become ** and *, links become [text](url), images become ![alt](src), and lists become - or numbered items. Code becomes backticks, a pre block becomes a fenced code block, and a blockquote gains its > markers. The result is Markdown you can paste straight into a docs site or a CMS.

Two things are dropped on purpose. Scripts and styles are removed entirely — Markdown has no place for them, and carrying them over would be a security risk in most destinations. Tables, div wrappers and span elements are not dropped, but their structure is: their text passes through as plain paragraphs, so a table becomes its cell text in reading order. If the table matters, rebuild it as a Markdown table by hand.

Why turn HTML into Markdown?

The usual reason is a move: content written for a website has to live in a documentation system, a wiki, a static site generator or a CMS that speaks Markdown. Copying the rendered text loses the links and the structure; copying the HTML keeps the structure but in the wrong format. Converting gives you the content in the format the new home expects, with links and headings intact.

It is also a cleaning step. HTML copied from a web page carries classes, inline styles and tracking attributes that you do not want. Converting to Markdown strips all of that away and leaves the words, the links and the structure — a clean source you can edit, version-control and publish anywhere.

Big migrations work the same way, one page at a time. Moving a WordPress site to a static generator, a Confluence space to a docs site, or a pile of old help articles into a new knowledge base all come down to the same loop: take the HTML, convert it, tidy the result, publish. The conversion is the fast part; the tidying — fixing relative links, rebuilding tables, checking images — is where the time goes, so budget for it.

Cleaning up after conversion

Three checks are worth doing on every conversion. First, links: relative links like /about stay relative, so if the new home lives on a different domain, make them absolute or re-point them. Second, images: the converter keeps the src and the alt text, but a relative image path needs the same treatment as a relative link. Third, tables: they arrive as plain text, so find them in the output and rebuild them as Markdown tables before publishing.

Nested lists survive the conversion with two-space indentation, which most Markdown renderers understand. Deeply nested structures and multi-paragraph list items are the edge cases — read them once in the output and tidy the indentation if your renderer complains.
