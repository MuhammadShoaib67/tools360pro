Formatting plus validation in one pass

XML is stricter than HTML: every tag must close, attributes must be quoted, and there must be exactly one root element. A formatter for XML therefore does two jobs. First it checks the document with the browser's own XML parser, which is the same strict parser a server or an importer would use. If the document fails, you get the parser's error message instead of a guess. Only if it passes does the formatting step run.

The formatting itself is straightforward: one element per line, children indented under their parent, and elements that hold only text kept on a single line so the output stays compact. Attributes stay on the opening tag, in their original order. Comments and CDATA sections are preserved, and the XML declaration at the top of the file is kept.

The errors that break XML most often

Most invalid XML fails for a small handful of reasons. An unclosed tag is the classic one — XML has no void elements, so every opening tag needs its close. Mismatched case is another: <Title> closed by </title> is an error, because XML tag names are case-sensitive. Unescaped ampersands and angle brackets inside text are a third — a bare & in a product name must be written as &amp;, and a < in a comparison as &lt;.

Two structural errors round out the list: more than one root element, and text or markup sitting outside the root. The parser stops at the first problem it meets, so a large file often hides two or three errors — fix the reported one, format again, and repeat until the document passes cleanly.

When to format, when to leave it alone

Format XML when a human has to read or fix it: a configuration file, an API response you are debugging, a sitemap, an RSS feed, a data export. Indentation turns a single dense line into a structure you can scan, and the element count in the success message gives a quick sense of the document's size.

Leave it minified when only machines read it. A feed or an API response that travels over a network is smaller and faster as one line, and formatting it would only add bytes. The rule is the same as for JSON: pretty-print for people, compact for transport, and never edit the minified copy by hand when a formatted one exists.

Frequently asked questions

What does the validator check?

It checks well-formedness: one root element, every tag closed, matching case, quoted attributes and no stray text outside the root. It uses the browser's own XML parser, so the verdict matches what a server or importer would say.

Why does my XML fail with a parser error?

The usual causes are an unclosed tag, mismatched tag case, an unescaped ampersand or angle bracket in text, or more than one root element. The error message names the problem and usually the line, so fix that spot and try again.

Are comments and CDATA sections kept?

Yes. Comments are preserved in place, CDATA sections are kept intact, and the XML declaration at the top of the file is carried over to the formatted output.

Does it check against a schema or DTD?

No. This tool checks that the document is well-formed XML, not that it matches a particular schema, DTD or expected structure. Schema validation needs a dedicated validator.

Is my XML uploaded anywhere?

No. This tool runs entirely in your browser using JavaScript. Your data is never uploaded, stored or sent anywhere — everything stays on this device.
